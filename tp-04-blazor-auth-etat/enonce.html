Vocabulaire : l'authentification établit qui est l'utilisateur ; l'autorisation décide ce qu'il a le droit de faire. En .NET, un utilisateur est un ClaimsPrincipal : un ensemble de claims (nom, rôles, e-mail…) émis par un schéma d'authentification (jeton JWT, cookie…).

Authentifier les appels à l'API avec un JWT

  1. Ajoutez le package au projet de l'API : dotnet add depart/src/Tickets.Api package Microsoft.AspNetCore.Authentication.JwtBearer. La version vient du fichier central.
  2. Dans Program.cs, enregistrez l'authentification par jeton : AddAuthentication().AddJwtBearer(). Sans argument, elle lit la section Authentication:Schemes:Bearer de la configuration.
  3. Ajoutez une route GET /me, réservée aux utilisateurs authentifiés, qui renvoie name, roles et isAdmin à partir du ClaimsPrincipal.
  4. Créez deux jetons de développement, depuis depart/src/Tickets.Api : 
    dotnet user-jwts create --name alice
dotnet user-jwts create --name admin --role admin
    L'outil range la clé de signature dans user-secrets et complète appsettings.Development.json. Regardez ce qu'il a écrit.
  5. Appelez /me sans jeton (401), puis avec : curl -H "Authorization: Bearer <jeton>" http://localhost:5080/me. Collez le jeton sur jwt.io pour voir les claims.
la route
app.MapGet("/me", (ClaimsPrincipal user) => new
{
    Name = user.Identity?.Name,
    Roles = user.FindAll(ClaimTypes.Role).Select(claim => claim.Value).ToArray(),
    IsAdmin = user.IsInRole("admin"),
}).RequireAuthorization();
401 ou 404 ?

Un 404 sur /me signifie que la route n'existe pas encore. Un 200 sans jeton, qu'il manque .RequireAuthorization(). Un 401 avec un jeton valide, que l'audience ou l'émetteur ne correspondent pas : vérifiez appsettings.Development.json.

Comparaison

≈ Spring Security en resource server : oauth2ResourceServer().jwt(). ClaimsPrincipal ≈ l'objet Authentication, et le Jwt injecté.

Avec Axum, on écrit souvent un extracteur qui décode le jeton avec la crate jsonwebtoken. Ici, le schéma JWT est fourni et configuré par la configuration.

≈ HTTPBearer de FastAPI et PyJWT dans une dépendance. ASP.NET Core le fait dans un middleware, avant la route.

≈ express-jwt : un middleware qui valide le jeton et remplit req.auth, ici HttpContext.User.

struct User { name: String }

impl<S: Send + Sync> FromRequestParts<S> for User {
    type Rejection = StatusCode;

    async fn from_request_parts(parts: &mut Parts, _: &S) -> Result<Self, Self::Rejection> {
        let token = parts.headers.get(AUTHORIZATION)
            .and_then(|value| value.to_str().ok()?.strip_prefix("Bearer "))
            .ok_or(StatusCode::UNAUTHORIZED)?;
        let claims = decode::<Claims>(token, &KEY, &Validation::default())
            .map_err(|_| StatusCode::UNAUTHORIZED)?
            .claims;
        Ok(User { name: claims.sub })
    }
}

async fn me(user: User) -> String { user.name }
bearer = HTTPBearer()

def current_user(credentials: HTTPAuthorizationCredentials = Depends(bearer)) -> str:
    try:
        claims = jwt.decode(credentials.credentials, KEY, algorithms=["HS256"], audience="tickets-api")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401)
    return claims["sub"]

@app.get("/me")
def me(user: str = Depends(current_user)):
    return {"name": user}
import { expressjwt } from "express-jwt";

app.use("/me", expressjwt({ secret: KEY, algorithms: ["HS256"], audience: "tickets-api" }));
app.get("/me", (req, res) => res.json({ name: req.auth.sub }));

401 ou 403 ?

401 Unauthorized : on ne sait pas qui vous êtes (pas de jeton, ou jeton invalide). 403 Forbidden : on sait qui vous êtes, et vous n'avez pas le droit. ASP.NET Core choisit tout seul selon le cas.

Comparaison

≈ authorizeHttpRequests et hasRole, ou @PreAuthorize sur la méthode. Une policy nommée permet de réutiliser une règle sans la répéter.

≈ un middleware route_layer qui vérifie le rôle, posé sur un sous-routeur.

≈ une dépendance require_admin posée sur la route avec dependencies=[…].

≈ un middleware Express requireRole("admin") intercalé avant le gestionnaire.

async fn require_admin(user: User, request: Request, next: Next) -> Result<Response, StatusCode> {
    if !user.roles.iter().any(|role| role == "admin") {
        return Err(StatusCode::FORBIDDEN);
    }
    Ok(next.run(request).await)
}

Un front qui connaît son utilisateur

Le front utilise une autre méthode d'authentification : un cookie, écrit par la page de connexion fournie. Ses deux comptes de démonstration sont alice et admin, mot de passe demo. Dans une vraie appli, la connexion passerait par OpenID Connect vers notre fournisseur d'identité, et aucun mot de passe ne transiterait par notre code.

  1. Les services : dans Tickets.Web/Program.cs, enregistrez l'authentification par cookie (page de connexion /account/login), l'autorisation, et AddCascadingAuthenticationState() qui fournit l'utilisateur à tous les composants.
  2. Le menu : dans NavMenu.razor, avec <AuthorizeView>, affichez « Hello, alice », la mention administrator pour le rôle admin, et un formulaire de déconnexion (POST account/logout, déjà prévu).   3. La page protégée : réservez NewTicket.razor aux utilisateurs connectés avec @attribute [Authorize]. Dans Routes.razor, remplacez RouteView par AuthorizeRouteView.
  4. Le jeton vers l'API : depuis l'exercice 2, l'API refuse les créations anonymes. Complétez Security/ApiTokenHandler.cs, branchez-le sur le client HTTP typé, puis donnez au front un jeton de service : 
    dotnet user-jwts create --project depart/src/Tickets.Api --name tickets-web --output token

Partager de l'état entre composants

Deux façons de faire circuler une information sans la passer de parent en enfant :

  • un service scoped : une instance par circuit, donc par utilisateur et par onglet en mode Server, que tous les composants peuvent injecter ;
  • une valeur en cascade : un ancêtre la fournit avec <CascadingValue>, et tous ses descendants la reçoivent.
  1. Complétez Tickets.Web.Client/State/FavoritesState.cs (les identifiants des tickets favoris, et l'événement Changed), et enregistrez-le en scoped dans les deux Program.cs.
  2. Dans TicketCard, ajoutez un bouton de classe favorite qui bascule le ticket dans les favoris et affiche ★ ou ☆.
  3. Écrivez FavoritesCounter.razor (le TODO le décrit) et placez-le au-dessus de la liste dans TicketList. Il doit se mettre à jour quand on clique sur une carte, donc dans un autre composant.
  4. Ajoutez à TicketList une case à cocher Compact, et transmettez sa valeur à toutes les cartes avec <CascadingValue Name="Compact" Value="_compact">. Une carte compacte n'affiche pas la description.
le service
private readonly HashSet<int> _ticketIds = [];

public void Toggle(int ticketId)
{
    if (!_ticketIds.Remove(ticketId)) { _ticketIds.Add(ticketId); }
    Changed?.Invoke();
}
se mettre à jour

Dans le compteur : @implements IDisposable, puis Favorites.Changed += OnChanged dans OnInitialized, avec private void OnChanged() => InvokeAsync(StateHasChanged);, et -= dans Dispose. Sans désabonnement, le service garderait une référence vers un composant mort.

recevoir la cascade

Dans TicketCard : [CascadingParameter(Name = "Compact")] public bool Compact { get; set; }.

Comparaison

Avec Vaadin, un bean @UIScope partagé par les vues d'un onglet joue le rôle du service scoped ; les écouteurs remplacent l'événement Changed.

≈ provide_context et expect_context de Leptos avec un signal : la réactivité est automatique, alors qu'en Blazor on s'abonne à un événement.

Côté serveur, l'état par utilisateur vit dans la session ; chaque requête relit et réécrit le fragment HTML concerné.

Le service scoped ≈ un store Zustand ou un contexte React ; CascadingValue ≈ Context.Provider, sans le ré-affichage automatique des abonnés.

Un seul chargement malgré le prérendu

Hier, /tickets appelait l'API deux fois : au prérendu, puis au démarrage du circuit interactif. .NET 10 propose [PersistentState] : la valeur calculée au prérendu est enregistrée dans la page, puis restaurée avant OnInitializedAsync.

  1. Dans TicketList.razor, transformez le champ des tickets en propriété publique marquée [PersistentState].
  2. Dans OnInitializedAsync, ne chargez que si la propriété est encore vide.
  3. Rechargez /tickets et comptez les GET /tickets dans la console de l'API : un seul par affichage.
  4. Affichez le source de la page : un commentaire <!--Blazor-Server-Component-State:…--> transporte l'état, chiffré. Le test le déchiffre pour y chercher vos tickets.
la propriété
[PersistentState]
public IReadOnlyList<TicketDto>? Tickets { get; set; }

protected override async Task OnInitializedAsync()
{
    Tickets ??= await Client.GetTicketsAsync();
}
Comparaison

Avec Thymeleaf, rien de tel n'existe puisqu'il n'y a qu'un rendu ; quand du JavaScript prend le relais, on embarque soi-même les données dans la page.

Leptos le fait pour toute Resource : les données chargées au rendu serveur sont sérialisées et réutilisées à l'hydratation.

Même principe qu'en Java : on embarque les données en JSON dans le template, avec le filtre tojson.

≈ l'hydratation de Next.js : les props calculées côté serveur voyagent dans la page (__NEXT_DATA__) et ne sont pas rechargées.

[PersistentState]

protected override async Task OnInitializedAsync() =>
    Products ??= await Client.GetProductsAsync();   // sauté si l'état a été restauré

</script>

// puis réutilisée à l'hydratation sans second appel.

<!-- Jinja2 : les données voyagent en JSON dans la page -->

Extraire un composant dans une bibliothèque

Une Razor Class Library (RCL) regroupe des composants, leurs styles et leurs fichiers statiques, réutilisables dans plusieurs applis et distribuables en package NuGet. On y place un composant Badge générique, sans rien qui concerne les tickets ; PriorityBadge devient une simple adaptation.

  1. Créez la bibliothèque, depuis depart/ : 
    dotnet new razorclasslib -n Tickets.Components -o src/Tickets.Components
dotnet sln Tickets.slnx add src/Tickets.Components
dotnet add src/Tickets.Web.Client reference src/Tickets.Components
  2. Supprimez les fichiers d'exemple (Component1.*, ExampleJsInterop.cs, wwwroot/), et retirez l'attribut Version du PackageReference dans le .csproj : la gestion centralisée des versions l'interdit (erreur NU1008).
  3. Créez Badge.razor dans l'espace de noms Tickets.Components : un paramètre Variant (par défaut neutral) et un ChildContent, rendus en <span class="badge badge-@Variant">. Déplacez la règle .badge d'app.css vers Badge.razor.css.
  4. Ajoutez @using Tickets.Components aux _Imports.razor du client et du serveur, et réécrivez PriorityBadge en une ligne avec <Badge>.
  5. Les styles de la bibliothèque sont servis sous _content/Tickets.Components/ : vérifiez-le dans l'onglet Réseau.
Badge
<span class="badge badge-@Variant">@ChildContent</span>

@code {
    [Parameter] public string Variant { get; set; } = "neutral";
    [Parameter] public RenderFragment? ChildContent { get; set; }
}
PriorityBadge
<Badge Variant="@Priority.ToString().ToLowerInvariant()">@Priority</Badge>

Le HTML produit est identique à avant ; seul l'attribut b-xxxx du CSS isolé de Badge apparaît. C'est ce que vérifie un test.
