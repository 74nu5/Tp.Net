Blazor : composants, modes de rendu et formulaires

Blazor écrit des interfaces web en C# avec des composants, comme React ou Vue, et c'est l'outil de la plupart de nos applis. Ce matin, vous construisez le front de l'API de tickets d'hier : composants, chargement de données, modes de rendu, formulaire validé, grille triée et un peu de JavaScript.

Cochez « Terminé » à la fin de chaque exercice ; le chrono est facultatif. Tout reste dans ce navigateur.

Les exemples de code montrent Blazor, et à côté l'équivalent dans l'écosystème de votre choix :

Avant de commencer

  1. depart/ contient la solution du TP-02 (l'API) et deux nouveaux projets : Tickets.Web, l'application Blazor, et Tickets.Web.Client, les composants qui peuvent aussi s'exécuter dans le navigateur.

Anatomie d'une Blazor Web App

Parcourez les fichiers dans cet ordre :

  1. Program.cs : AddRazorComponents() et les deux modes interactifs, puis MapRazorComponents<App>(). AddAdditionalAssemblies ajoute les pages du projet client.
  2. Components/App.razor : la page HTML complète. <Routes /> affiche la page demandée, et blazor.web.js rend la page interactive quand il le faut.
  3. Components/Routes.razor : le routeur, qui associe une adresse à un composant portant @page, et le layout par défaut.
  4. Components/Layout/MainLayout.razor et NavMenu.razor : le cadre commun, et @Body à l'endroit où la page s'insère.
  5. Components/_Imports.razor : les @using communs à tous les composants du dossier.

Ajoutez une page Components/Pages/About.razor à l'adresse /about, avec un <PageTitle>, un <h1>About</h1> et l'heure du serveur. Ajoutez le lien dans NavMenu.razor.

Question

L'heure change quand vous rechargez la page. Cette page est-elle interactive ?

Voir la réponse

Non. Sans mode de rendu, une page est rendue statiquement sur le serveur (Static SSR) : du HTML calculé à chaque requête, sans connexion persistante ni événement. Un bouton @onclick n'y ferait rien. L'exercice 4 compare les modes.

Composants, paramètres et événements

Un composant .razor mélange du HTML et du C#. Il reçoit des paramètres de son parent, et lui renvoie des événements. Dans Tickets.Web.Client/Components/, suivez les TODO :

  1. PriorityBadge : un paramètre Priority, affiché dans un <span class="badge badge-high"> dont la classe suit la priorité.
  2. TicketCard : un paramètre Ticket obligatoire, un événement OnSelected déclenché par un bouton Select, et un ChildContent affiché dans le pied de la carte. La carte réutilise PriorityBadge.
un paramètre
@code {
    [Parameter, EditorRequired]
    public TicketDto Ticket { get; set; } = default!;
}

EditorRequired fait signaler par l'IDE un parent qui oublie le paramètre.

un événement vers le parent

Un paramètre EventCallback<TicketDto> OnSelected, et dans le bouton : @onclick="() => OnSelected.InvokeAsync(Ticket)". Le parent est ré-affiché automatiquement après son gestionnaire.

du contenu libre

Un paramètre nommé exactement ChildContent, de type RenderFragment?, reçoit ce que le parent écrit entre les balises : <TicketCard Ticket="t">ici</TicketCard>. On l'affiche avec @ChildContent.

Comparaison

Le plus proche en Java est Vaadin : des composants avec un état côté serveur. [Parameter] ≈ un argument de constructeur, EventCallback ≈ un listener.

Très proche d'un composant Leptos ou Yew : propriétés typées, Callback pour les événements, Children pour le contenu.

Côté Python, le plus proche est une macro Jinja2 avec caller() pour le contenu ; l'interactivité passe par le serveur, avec HTMX par exemple.

Comme React : [Parameter] ≈ les props, EventCallback ≈ une fonction passée en prop, ChildContent ≈ children.

Charger des données : le cycle de vie

Dans Components/Pages/TicketList.razor, chargez les tickets au démarrage du composant avec ITicketsClient, déjà injecté. Gérez les quatre états que décrit le TODO : chargement, erreur, liste vide, liste. Chaque ticket s'affiche avec votre TicketCard ; la carte sélectionnée s'affiche au-dessus de la liste.

Ouvrez ensuite /tickets avec l'API lancée, et regardez la console de l'API : combien d'appels à GET /tickets pour un seul affichage ?

au démarrage

Redéfinissez protected override async Task OnInitializedAsync(). Blazor ré-affiche le composant quand la méthode se termine.

les états

Trois champs suffisent : IReadOnlyList<TicketDto>? _tickets (null pendant le chargement), string? _error et TicketDto? _selected. Dans le balisage : @if (_error is not null) { … } else if (_tickets is null) { … } else if ….

la liste

@foreach (var ticket in _tickets) { <TicketCard @key="ticket.Id" Ticket="ticket" OnSelected="Select" /> }, avec private void Select(TicketDto ticket) => _selected = ticket;. @key aide Blazor à associer chaque carte à son ticket quand la liste change.

Pourquoi deux appels à l'API ?

La page est prérendue : le serveur calcule une première fois le HTML pour l'afficher tout de suite, puis le composant redémarre quand la connexion interactive s'établit, et OnInitializedAsync s'exécute à nouveau. Demain, le TP-04 supprime ce second appel en conservant l'état du prérendu.

Comparaison

Avec Vaadin, on charge dans le constructeur de la vue, côté serveur. OnInitializedAsync joue ce rôle, en asynchrone.

≈ une Resource Leptos dans un <Suspense>. Ici on gère l'état « en cours » soi-même, avec un champ null.

Avec HTMX, le fragment se charge après la page via hx-trigger="load" ; Blazor fait l'équivalent dans le composant.

≈ useEffect(…, []) avec un useState. Pas de tableau de dépendances : OnInitializedAsync ne s'exécute qu'une fois par instance du composant.

Les modes de rendu

C'est la notion la plus importante de Blazor. Un même composant peut s'afficher de quatre façons :

ModeOù tourne le codeInteractifBon choix pour
Static SSR (par défaut)serveur, une fois par requêtenonpages de contenu, formulaires simples
InteractiveServerserveur ; le navigateur envoie les événements par SignalRouiapplis métier, accès direct aux services et à la base
InteractiveWebAssemblynavigateur, .NET compilé en WebAssemblyouiinterfaces riches, hors connexion, charge serveur réduite
InteractiveAutoserveur au premier affichage, puis navigateurouidémarrage rapide et WebAssembly ensuite

Les pages de Components/Pages/RenderModes/ affichent toutes le même composant RenderModeProbe, fourni. Donnez-lui le bon mode de rendu dans les pages server, webassembly et auto, puis, pour chaque page :

  1. lisez Renderer et Interactive, et cliquez sur le bouton ;
  2. ouvrez les outils de développement, onglet Réseau : une connexion WebSocket /_blazor en mode Server, le téléchargement de fichiers .wasm en mode WebAssembly ;
  3. affichez le source de la page (Ctrl+U) : le HTML est déjà là, c'est le prérendu, et un commentaire <!--Blazor:{"type":"server",…}--> indique à blazor.web.js quoi rendre interactif. Ce sont ces marqueurs que vérifient les tests.

En mode Auto, la première visite passe par le serveur, le temps que le navigateur télécharge le runtime .NET ; les visites suivantes passent en WebAssembly.

la syntaxe

Sur l'instance du composant : <RenderModeProbe Label="…" @rendermode="InteractiveServer" />. Ou pour toute une page : la directive @rendermode InteractiveServer en tête de fichier, comme dans TicketList.razor.

pourquoi deux projets ?

Un composant rendu en WebAssembly est téléchargé dans le navigateur : il doit vivre dans Tickets.Web.Client, et il n'a pas accès aux services du serveur (base de données, secrets). C'est pour cela que RenderModeProbe y est rangé.

Question

Pour un back-office interne qui lit et écrit en base, quel mode choisiriez-vous par défaut, et pourquoi ?

Voir la réponse

Souvent InteractiveServer : le code accède directement aux services du serveur, rien n'est téléchargé, et le réseau d'entreprise supporte bien la connexion SignalR permanente. Ses limites : chaque utilisateur occupe de la mémoire sur le serveur, et une coupure réseau fige l'écran le temps de la reconnexion. WebAssembly devient intéressant pour de nombreux utilisateurs externes ou des écrans très interactifs.

Comparaison

Interactive Server ≈ Vaadin : l'état vit sur le serveur, le navigateur envoie les événements par une connexion persistante. Static SSR ≈ Thymeleaf.

Interactive WebAssembly ≈ Leptos ou Yew compilés en .wasm, avec hydratation après un rendu serveur.

Static SSR ≈ Jinja2. Interactive Server ressemble à HTMX poussé jusqu'au bout : chaque événement fait un aller-retour serveur, mais sur une connexion ouverte et sans écrire de fragment HTML.

≈ les composants serveur de Next.js (Static SSR) et "use client" (hydratés dans le navigateur, ≈ WebAssembly). Interactive Server n'a pas d'équivalent courant en JS.

le chemin, et le nettoyage

Le module est servi au même chemin que le fichier .razor. Dans une Blazor Web App, les fichiers du projet client sont servis à la racine du site ; dans une bibliothèque de composants, ce serait _content/<bibliothèque>/…. Libérez le module en implémentant IAsyncDisposable, et ignorez JSDisconnectedException : en mode Server, le navigateur peut être déjà parti.
