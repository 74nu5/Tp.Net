Le débogueur : points d'arrêt conditionnels et Hot Reload

L'ancien outil a exporté 240 tickets ; l'import n'en crée que 237. Aucune erreur, aucun log : trois tickets disparaissent. Le parseur est dans src/Tickets.Api/Import/TicketCsvParser.cs.

  1. Lancez le test TheSample_GivesOneTicketPerLine : il attend 240 tickets et en reçoit 237.
  2. Lancez ce même test en débogage depuis l'IDE (Rider : icône dans la marge, puis Debug ; Visual Studio : clic droit dans l'explorateur de tests, Debug ; VS Code : Debug Test au-dessus de la méthode).
  3. Posez un point d'arrêt sur la ligne if (fields.Length == FieldCount). Il s'arrête à chaque ligne du fichier : 240 fois. Rendez-le conditionnel (clic droit sur le point d'arrêt) avec la condition fields.Length != FieldCount.
  4. Au premier arrêt, regardez les variables locales : lineNumber, line, fields. Ajoutez un espion (watch) sur fields.Length. Notez le numéro de la ligne dans tests/Tickets.Tests/Answers.cs (FirstSkippedLine).
  5. Sans vous arrêter, listez toutes les lignes perdues avec un point de trace (Visual Studio : Actions ; Rider : Log evaluated expression ; VS Code : Logpoint) qui écrit {lineNumber}: {fields.Length} dans la sortie de débogage.
  6. Corrigez le parseur : un champ entre guillemets peut contenir des virgules, et "" dans un champ entre guillemets vaut un guillemet (RFC 4180). Une ligne qui reste mal formée doit arrêter l'import avec une FormatException qui donne son numéro (« Line 3: … ») : perdre des données en silence est pire qu'une erreur.
  7. Hot Reload : lancez dotnet watch --project depart/src/Tickets.Api, ouvrez http://localhost:5080/, changez le texte renvoyé par app.MapGet("/", …) dans Program.cs, enregistrez, puis rechargez la page : elle affiche le nouveau texte sans que l'API ait redémarré. Certaines modifications, dites rude edits, ne peuvent pas s'appliquer à chaud : dotnet watch propose alors de redémarrer.
la condition ne s'arrête jamais

La condition est une expression C# évaluée dans le contexte de la ligne : les variables doivent déjà exister à cet endroit. Placez le point d'arrêt sur le if, après var fields = …, pas sur la ligne qui déclare fields.

découper en respectant les guillemets

Parcourez la ligne caractère par caractère avec un booléen inQuotes. Hors guillemets, une virgule termine le champ. Dans les guillemets, "" ajoute un guillemet et " seul referme. Un StringBuilder accumule le champ en cours.

le découpage complet
public static IReadOnlyList<string> SplitFields(string line)
{
    var fields = new List<string>();
    var current = new StringBuilder();
    var inQuotes = false;

    for (var i = 0; i < line.Length; i++)
    {
        var c = line[i];
        if (inQuotes)
        {
            if (c == '"' && i + 1 < line.Length && line[i + 1] == '"')
            {
                current.Append('"');
                i++;
            }
            else if (c == '"') inQuotes = false;
            else current.Append(c);
        }
        else if (c == '"') inQuotes = true;
        else if (c == ',')
        {
            fields.Add(current.ToString());
            current.Clear();
        }
        else current.Append(c);
    }

    fields.Add(current.ToString());
    return fields;
}

Pourquoi ce code compile-t-il, alors qu'il échoue à chaque appel ?

Voir la réponse

Une requête EF Core est un IQueryable : le lambda t => t.CommentCount n'est pas compilé en code mais en arbre d'expression, qu'EF Core traduit en SQL au moment de l'exécution. Le compilateur C# vérifie les types, pas la traduisibilité. CommentCount est une propriété calculée en C#, sans colonne : EF ne sait pas l'écrire en SQL.

Le message propose d'ajouter AsEnumerable() avant Sum. Bonne idée ?

Voir la réponse

Non. Le calcul passerait côté C# après avoir chargé tous les tickets, et Comments ne serait pas chargé (pas d'Include) : la somme vaudrait 0, sans erreur. Le bon correctif reste en SQL : await db.Comments.CountAsync(cancellationToken).

Pourquoi les frames d'EF Core n'ont-elles pas de numéro de ligne ?

Voir la réponse

Les numéros de ligne viennent des fichiers de symboles (.pdb) produits par notre compilation, en Debug comme en Release. Pour les packages, il faut les symboles publiés et Source Link : Rider et Visual Studio savent alors entrer dans le code d'EF Core en débogage.

Deux formes reviennent souvent dans une stack trace .NET : ---> introduit une InnerException (l'erreur d'origine, enveloppée dans une autre), et --- End of stack trace from previous location --- marque un await où l'exception a été relancée. Lisez toujours jusqu'à l'exception la plus intérieure.

la première frame de notre code

Les frames Microsoft.* et System.* sont celles du framework. La première frame Tickets.* en partant du haut, avec un fichier et une ligne, est EfTicketRepository.GetStatsAsync.

le correctif
var comments = await db.Comments.CountAsync(cancellationToken);
Comparaison

Même ordre qu'en Java : la frame la plus profonde en haut. ---> correspond à Caused by:, mais .NET affiche l'exception intérieure avant l'extérieure. Hibernate échoue aussi à l'exécution sur une requête JPQL invalide.

Une panic! affiche sa backtrace avec RUST_BACKTRACE=1. Une Result::Err n'en a pas, sauf avec anyhow ou std::backtrace. En .NET, toute exception porte sa stack trace.

Attention, l'ordre est inversé : le traceback Python finit par l'appel le plus récent (most recent call last), .NET commence par lui. ---> ≈ The above exception was the direct cause…

≈ err.stack, du plus profond au plus haut, comme en .NET. V8 garde les frames at async au-delà des await, comme le fait .NET. ---> ≈ err.cause.

try { await repository.GetStatsAsync(ct); }

{

    // le message, la stack trace et les InnerException.

    throw;   // relance sans perdre la stack trace (pas "throw exception;")

    // SLF4J : l'exception en dernier argument donne la stack trace
    log.error("Stats failed", e);
    throw e;
}
// anyhow : with_context ajoute une couche, comme une InnerException
let stats = repository.get_stats().await
    .with_context(|| "stats failed")?;

// {:?} affiche la chaîne des causes, et la backtrace
// si RUST_BACKTRACE=1
try:
    stats = repository.get_stats()
except Exception:
    # logger.exception ajoute le traceback au message
    logger.exception("Stats failed")
    raise
try {
  await repository.getStats();
} catch (err) {
  // cause chaîne les erreurs, comme InnerException
  throw new Error("Stats failed", { cause: err });
}

Régler les logs : niveaux par catégorie et logs structurés

Deux plaintes de l'exploitation : en production, les logs sont noyés sous le SQL ; et quand on cherche « le ticket 42 a-t-il été fermé ? », il faut chercher du texte.

  1. Ouvrez appsettings.json de l'API. Chaque clé de Logging:LogLevel est une catégorie : le nom complet de la classe qui logge (ILogger<T>). Une clé vaut pour toutes les catégories qui commencent par elle, et la plus précise l'emporte.
  2. Le SQL d'EF Core est loggé par la catégorie Microsoft.EntityFrameworkCore.Database.Command. Ne le gardez qu'en développement : "Microsoft.EntityFrameworkCore": "Warning" dans appsettings.json, et la catégorie des commandes en Information dans appsettings.Development.json.
  3. La configuration s'empile, comme au TP-02 : une variable d'environnement l'emporte sur les fichiers. Essayez Logging__LogLevel__Default=Debug dotnet run --project depart/src/Tickets.Api (sous PowerShell : $env:Logging__LogLevel__Default="Debug" d'abord).
  4. Dans EfTicketRepository.CloseAsync, le log de fermeture est une chaîne interpolée. Remplacez-le par un message généré TicketClosed dans Data/TicketLog.cs, sur le modèle de TicketsImported : "Ticket {TicketId} closed after {OpenHours} hours", identifiant d'événement 1001.

Les deux lignes affichent le même texte. Qu'est-ce qui change ?

logger.LogInformation($"Ticket {ticket.Id} closed after {openHours} hours");
logger.TicketClosed(ticket.Id, openHours);
Voir la réponse

La chaîne interpolée est construite avant l'appel : le log ne reçoit que du texte, même quand le niveau est désactivé. Le message à modèle garde TicketId et OpenHours comme des champs : Aspire, Seq ou Elastic peuvent filtrer sur TicketId = 42. [LoggerMessage] génère en plus, à la compilation, un code qui ne fait rien quand le niveau est désactivé. C'est aussi ce que signale l'analyseur CA2254.

quel fichier pour quel environnement

appsettings.json est lu partout ; appsettings.Development.json s'ajoute par-dessus quand ASPNETCORE_ENVIRONMENT vaut Development, comme dans le profil de lancement. Les tests vérifient les deux environnements.

le message généré
[LoggerMessage(EventId = 1001, Level = LogLevel.Information, Message = "Ticket {TicketId} closed after {OpenHours} hours")]
public static partial void TicketClosed(this ILogger logger, int ticketId, double openHours);
Comparaison

Les catégories ≈ les noms de loggers de Logback (logging.level.org.hibernate.SQL=debug dans Spring Boot). Les accolades de SLF4J sont positionnelles ; pour des champs nommés, SLF4J 2 a une API fluide.

≈ tracing et le filtre RUST_LOG=tickets=info,sqlx=warn. Les champs nommés de tracing sont exactement des logs structurés.

Les catégories ≈ la hiérarchie de logging.getLogger("a.b"). Le formatage avec %s est différé comme ici ; pour des champs, extra= ou structlog.

≈ pino ou winston : un objet de champs plus un message. Les niveaux par catégorie ≈ des loggers enfants avec leur propre niveau.

Aperçu de .NET 11 : les unions de C# 15

.NET 11 sort en novembre 2026 ; ce n'est pas une version LTS, nos applis restent sur .NET 10. Mais C# 15 apporte une nouveauté attendue depuis longtemps : les unions, l'équivalent des enums de Rust ou des unions discriminées de TypeScript. On l'essaie dans un petit projet à part, net11/.

  1. Installez le SDK .NET 11 et vérifiez avec dotnet --list-sdks que les deux versions sont là. Dans net11/, dotnet --version donne la version 11 : son global.json la choisit. Ailleurs dans le dépôt, c'est toujours .NET 10.
  2. Ouvrez net11/depart/src/Tickets.Preview/TicketBoard.cs. Fermer un ticket a trois issues : Closed, NotFound, AlreadyClosed. L'union CloseResult n'en contient que deux, et Close lève une exception pour la troisième.
  3. Lancez les tests (commande ci-dessus) : ClosingTwice_GivesAlreadyClosed échoue.
  4. Ajoutez AlreadyClosed à l'union et compilez. Le compilateur refuse : les deux switch ne traitent pas le nouveau cas (CS8509, transformée en erreur dans ce projet). Complétez-les, renvoyez AlreadyClosed dans Close : les tests passent.

Dans l'API, CloseAsync renvoie (TicketChange Result, Ticket? Ticket). Qu'apporte l'union par rapport à ce tuple ?

Voir la réponse

Avec le tuple, rien n'empêche de lire Ticket quand le résultat est NotFound : il vaut null, et le ! du code d'appel le cache. Avec l'union, chaque cas porte exactement ses données (NotFound n'a qu'un identifiant), et le compilateur vérifie que chaque switch traite tous les cas. Ajouter un cas montre tous les endroits à mettre à jour.

Les autres nouveautés de C# 15 : des arguments dans les expressions de collection ([with(StringComparer.OrdinalIgnoreCase), …]), les hiérarchies fermées (closed, ≈ sealed de Java), les indexeurs d'extension, break et continue avec étiquette, et un nouveau modèle de sécurité mémoire pour unsafe. Côté runtime, l'async natif (Runtime Async, en préversion : <Features>runtime-async=on</Features> dans le projet) remplace les machines à états générées par le compilateur : la pile d'appels que montre le débogueur dans du code async ne contient plus que vos méthodes. Pour suivre :

  • What's new in C# 15 et What's new in .NET 11 sur Microsoft Learn ;
  • le blog .NET, avec un article par préversion ;
  • les propositions du langage sur dotnet/csharplang ;
  • la .NET Conf, en novembre, qui lance chaque version.

};
la date dans Describe

Un motif positionnel déconstruit le record, et un motif de propriété regarde à l'intérieur : AlreadyClosed({ ClosedAt: { } closedAt } ticket) => $"Ticket {ticket.Id} was already closed on {closedAt:yyyy-MM-dd}.". Gardez un cas AlreadyClosed(var ticket) pour un ticket sans date.

Comparaison

≈ une sealed interface avec des records (Java 17), et le switch exhaustif de Java 21. En C#, les cas n'ont pas à implémenter une interface commune : n'importe quels types peuvent former une union.

C'est l'enum de Rust et son match exhaustif. Différence : en C#, les cas sont des types qui existent par eux-mêmes (Closed est un record), pas des variantes déclarées dans l'union.

≈ Closed | NotFound | AlreadyClosed et match. Python ne vérifie l'exhaustivité qu'avec mypy ou pyright et assert_never ; ici, c'est le compilateur.

≈ une union discriminée de TypeScript. Pas besoin de champ kind : le switch C# teste le type du cas.

public sealed record Closed(Ticket Ticket);

{
    Closed => 200,
    NotFound => 404,
    AlreadyClosed => 409,
};

from dataclasses import dataclass
from typing import assert_never

@dataclass
class Closed:
    ticket: Ticket

@dataclass
class NotFound:
    id: int

@dataclass
class AlreadyClosed:
    ticket: Ticket

type CloseResult = Closed | NotFound | AlreadyClosed  # Python 3.12

    match result:
        case Closed():
            return 200
        case NotFound():
            return 404
        case AlreadyClosed():
            return 409
        case _:
            assert_never(result)   # vérifié par mypy / pyright

type CloseResult =
  | { kind: "closed"; ticket: Ticket }
  | { kind: "notFound"; id: number }
  | { kind: "alreadyClosed"; ticket: Ticket };

function statusCode(result: CloseResult): number {
  switch (result.kind) {
    case "closed": return 200;
    case "notFound": return 404;
    case "alreadyClosed": return 409;
  }
}

Trois tickets sont arrivés cette semaine. Pour chacun : reproduisez, trouvez la cause avec les outils du matin, corrigez, et écrivez la cause en une phrase dans depart/ANOMALIES.md. Chaque anomalie a sa classe de tests dans Exercise06Tests.cs.

Une méthode qui marche sur toutes les anomalies :

  1. Reproduire : le test échoue-t-il ? Sinon, reproduisez à la main (Scalar sur /scalar, ou le front) jusqu'à voir le symptôme.
  2. Observer sans rien changer : les logs SQL (exercice 3), une trace dans Aspire (exercice 4), un point d'arrêt (exercice 1), la stack trace s'il y a une exception (exercice 2).
  3. Formuler la cause en une phrase avant de corriger. Si vous n'y arrivez pas, vous n'avez pas encore trouvé.
  4. Corriger au plus près de la cause, puis relancer tous les tests : une correction ne doit rien casser ailleurs.

piste pour l'anomalie 3

« Chez moi ça marche » : qu'a votre base que la base neuve n'a pas ? Les tests de Anomaly3Tests appellent directement TicketStatistics.Compute ; lisez le message de l'exception.

les trois causes
  1. UpdateAsync charge le ticket avec AsNoTracking() : le contexte ne le suit pas, SaveChangesAsync ne voit aucune modification et n'envoie pas d'UPDATE. Retirez AsNoTracking().
  2. Le cache est lu avec la clé "tickets:summaries" et vidé avec "tickets:summary" : il n'est jamais vidé et expire au bout d'une minute. Une seule constante pour la clé.
  3. Average lève une exception sur une séquence vide, et une base neuve n'a aucun ticket fermé. Renvoyez null quand il n'y a rien à moyenner.
Comparaison

L'anomalie 1 existe en JPA : une entité détachée modifiée n'est pas enregistrée sans merge. AsNoTracking ≈ une entité lue hors du contexte de persistance.

Avec sqlx ou Diesel, pas de suivi des modifications : on écrit l'UPDATE. L'anomalie 1 ne peut pas exister ; en échange, chaque mise à jour s'écrit à la main.

SQLAlchemy suit les objets de sa session comme EF Core : un objet détaché (session.expunge) n'est plus enregistré au commit.

Prisma ne suit rien : update envoie l'UPDATE tout de suite. L'anomalie 1 vient du modèle unit of work d'EF Core.

// Suivi des modifications : on modifie l'objet, SaveChanges écrit l'UPDATE
var ticket = await db.Tickets.FirstAsync(t => t.Id == id, ct);
ticket.Title = title;
await db.SaveChangesAsync(ct);
// JPA : l'entité est suivie dans la transaction
@Transactional
public void rename(long id, String title) {
    Ticket ticket = entityManager.find(Ticket.class, id);
    ticket.setTitle(title);   // UPDATE au commit
}
// sqlx (PostgreSQL) : pas de suivi, on écrit l'UPDATE
sqlx::query("UPDATE tickets SET title = $1 WHERE id = $2")
    .bind(&title)
    .bind(id)
    .execute(&pool)
    .await?;
# SQLAlchemy : la session suit l'objet
ticket = session.get(Ticket, ticket_id)
ticket.title = title
session.commit()   # UPDATE ici
// Prisma : pas de suivi, l'UPDATE part tout de suite
await prisma.ticket.update({ where: { id }, data: { title } });
