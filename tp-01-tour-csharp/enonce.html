SDK, CLI et anatomie d'un projet

Pas de test automatique pour celui-ci : vous validez en répondant aux questions. Tout se fait avec la commande dotnet. Travaillez dans un dossier depart/sandbox/, ignoré par Git.

dotnet --info                 # SDK et runtimes installés

cd depart && mkdir sandbox && cd sandbox
dotnet new console -n Hello
cd Hello
dotnet run

Ouvrez Hello.csproj et Program.cs, puis répondez :

  1. Que signifie <TargetFramework>net10.0</TargetFramework> ?
    Voir la réponse

    C'est le Target Framework Moniker : le projet cible .NET 10. On peut en viser plusieurs avec <TargetFrameworks>.

  2. Program.cs n'a ni classe ni méthode Main. Comment le programme démarre-t-il ?
    Voir la réponse

    Ce sont des top-level statements : le compilateur génère la classe et la méthode Main à partir des instructions du fichier.

  3. Où le binaire est-il produit ? À quoi servent bin/ et obj/ ?
    Voir la réponse

    Dans bin/Debug/net10.0/. obj/ contient les fichiers intermédiaires (restauration des packages, code généré). Les deux sont ignorés par Git.

  4. Lancez dotnet publish -c Release. Qu'obtenez-vous, et où ?
    Voir la réponse

    Le dossier bin/Release/net10.0/publish/ : la DLL et ses dépendances, prêtes à déployer. Avec --self-contained ou une publication AOT, on obtient un exécutable autonome.

  5. Nullable et ImplicitUsings apparaissent dans Hello.csproj, mais aussi dans Directory.Build.props à la racine du dépôt. Comment MSBuild trouve-t-il ce fichier ?
    Voir la réponse

    MSBuild cherche Directory.Build.props (et Directory.Packages.props) en remontant les dossiers depuis le projet, et importe le premier trouvé. C'est ainsi qu'un réglage s'applique à tous les projets d'un dépôt.

Enfin, depuis .NET 10, un fichier C# seul se lance sans projet. Revenez dans depart/sandbox/ (cd ..) : un fichier .cs posé dans le dossier d'un projet en ferait partie. Créez-y hello.cs :

Console.WriteLine($"Hello from .NET {Environment.Version}");

et lancez dotnet run hello.cs.

Comme Java, C# est compilé en bytecode (IL) exécuté par une machine virtuelle (le CLR), avec un compilateur JIT.

Contrairement à Rust, le binaire produit n'est pas natif par défaut : c'est de l'IL exécuté par le runtime .NET, avec un ramasse-miettes. La publication AOT donne un exécutable natif.

Contrairement à Python, tout est compilé avant l'exécution : les erreurs de type apparaissent au build, pas au lancement.

Le SDK fait à la fois le travail de npm, du bundler et du compilateur TypeScript : une seule commande, dotnet.

Modéliser : class, struct, record et nullabilité

C# offre plusieurs façons de déclarer un type. Le bon choix dépend de ce que représente l'objet :

DéclarationÉgalitéUsage typique
classpar référenceobjet avec une identité, qui change dans le temps
structpar valeurpetite valeur, copiée à chaque affectation
record (classe)par valeurdonnée immuable : DTO, message, valeur métier
readonly record structpar valeurpetite valeur immuable : montant, coordonnée

Dans src/Katas/Exercise03/ :

  1. Money est une class : deux montants identiques ne sont pas égaux. Transformez-la en readonly record struct, implémentez l'opérateur + (exception InvalidOperationException si les devises diffèrent) et ToString() ("12.50 EUR").
  2. Customer : deux clients aux mêmes données doivent être égaux et avoir un ToString() lisible. Le nom est obligatoire, l'email est facultatif : exprimez-le dans le type.
  3. Order reste une class, car une commande a une identité. Implémentez Total et refusez une quantité nulle ou négative dans AddLine. Remarquez le primary constructor : class Order(int id, …).
  4. Nullabilité : le build affiche des avertissements CS8618 et CS8602. Corrigez Customer, puis CustomerDirectory, jusqu'à zéro avertissement. Quand l'email devient string?, le compilateur vous montre l'endroit à protéger dans EmailDomain.

Money

Un record struct positionnel : public readonly record struct Money(decimal Amount, string Currency). Pour copier en changeant une propriété : left with { Amount = … }.

Customer

Une propriété obligatoire : public required string Name { get; init; }. Un email facultatif : string?.

null et garde-fous

customer?.Name ?? "ANONYMOUS" combine ?. et ??. ArgumentOutOfRangeException.ThrowIfNegativeOrZero(quantity) fait la vérification de quantité en une ligne.

ToString

Pour formater sans dépendre de la culture de la machine : string.Create(CultureInfo.InvariantCulture, $"{Amount:0.00} {Currency}").

Comparaison

Un record C# ressemble beaucoup au record Java, avec en plus with pour copier en modifiant. string? joue le rôle d'Optional, mais sans objet enveloppe : c'est une annotation vérifiée par le compilateur.

Un record struct ≈ une struct avec #[derive(Clone, Copy, PartialEq)]. Les nullable reference types rappellent Option<T>, mais ne sont vérifiés qu'à la compilation, par des avertissements : rien n'empêche un null d'arriver à l'exécution si on les ignore.

Un record ≈ une @dataclass(frozen=True), mais vérifiée à la compilation. string? ≈ str | None, sauf que le compilateur avertit vraiment.

JavaScript n'a pas d'égalité par valeur : deux objets identiques ne sont jamais ===. Les records C# l'apportent. string? ≈ string | null en TypeScript strict.

public readonly record struct Point(int X, int Y);

var a = new Point(1, 2);
var b = a with { Y = 5 };                  // copie modifiée
Console.WriteLine(a == new Point(1, 2));   // True : égalité par valeur

string? nickname = null;                   // peut être null, et le compilateur le sait
public record Point(int x, int y) {}

var a = new Point(1, 2);
var b = new Point(a.x(), 5);               // pas de "with" en Java
System.out.println(a.equals(new Point(1, 2)));   // true

Optional<String> nickname = Optional.empty();
#[derive(Debug, Clone, Copy, PartialEq)]
struct Point { x: i32, y: i32 }

let a = Point { x: 1, y: 2 };
let b = Point { y: 5, ..a };               // struct update syntax
println!("{}", a == Point { x: 1, y: 2 });   // true

let nickname: Option<String> = None;
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Point:
    x: int
    y: int

a = Point(1, 2)
b = replace(a, y=5)                        # copie modifiée
print(a == Point(1, 2))                    # True

nickname: str | None = None
const a = Object.freeze({ x: 1, y: 2 });
const b = { ...a, y: 5 };                  // copie modifiée
console.log(a === { x: 1, y: 2 });         // false : comparaison par référence

let nickname = null;                       // en TypeScript : string | null

Pattern matching

Dans Exercise04/Shipping.cs, écrivez chaque méthode avec une switch expression.

  1. Cost(Order) : frais de port gratuits à partir de 100 EUR, 4,90 en France, 9,90 ailleurs dans l'Union européenne, 19,90 dans le reste du monde. Un article fragile ajoute 5,00, même quand le port est gratuit.
  2. Describe(object?) : décrit n'importe quelle valeur, selon les règles du commentaire XML de la méthode (null, entier négatif, chaîne vide, Money à zéro, tableau vide, tableau d'un seul élément…).
motifs de propriété

{ Total: >= 100m } => 0m combine un motif de propriété et un motif relationnel.

gardes

{ Country: var country } when EuropeanUnion.Contains(country) => …, et pour combiner : int and < 0.

tableaux

Les motifs de liste : int[] and [], int[] and [var single], int[] and [var first, .., var last]. Les branches sont testées de haut en bas : les plus spécifiques d'abord, _ en dernier.

Comparaison

Proche du switch avec motifs de Java 21, en plus concis : pas de case, et des motifs relationnels (< 0) directement.

Très proche de match. Différence importante : un cas oublié ne bloque pas la compilation, il donne un avertissement (CS8509) puis une exception à l'exécution. Le _ final est votre filet.

Proche du match de Python 3.10, mais c'est une expression qui renvoie une valeur, et les types sont vérifiés à la compilation.

JavaScript n'a pas de pattern matching : on enchaîne des if ou des ternaires. C'est l'un des gros gains en passant à C#.

var label = n switch
{
    < 0 => "négatif",
    0 => "zéro",
    _ => "positif",
};
Integer n = 42;
String label = switch (n) {
    case Integer i when i < 0 -> "négatif";
    case Integer i when i == 0 -> "zéro";
    case Integer i -> "positif";
};
let label = match n {
    i32::MIN..=-1 => "négatif",
    0 => "zéro",
    _ => "positif",
};
match n:
    case _ if n < 0:
        label = "négatif"
    case 0:
        label = "zéro"
    case _:
        label = "positif"
const label = n < 0 ? "négatif"
            : n === 0 ? "zéro"
            : "positif";

LINQ

Exercise05/SampleData.cs fournit 5 clients, 7 produits et 10 commandes : n'y touchez pas, les tests en dépendent. Dans SalesReport.cs, implémentez les 10 méthodes, chacune en une seule requête LINQ, de préférence en syntaxe méthode (.Where(…).Select(…)).

Question

Le constructeur de SalesReport fait _orders = [.. orders]. Pourquoi ne pas garder directement orders ? Pour le vérifier, écrivez dans votre hello.cs une requête avec un Select qui affiche quelque chose, parcourez-la deux fois, et observez.

Voir la réponse

Une requête LINQ sur IEnumerable<T> est paresseuse : elle ne s'exécute qu'au moment où on la parcourt, et elle se ré-exécute à chaque parcours. Si orders est une requête, chaque méthode du rapport la recalculerait. [.. orders] la matérialise une fois pour toutes.

Comparaison

Exemple : les numéros des 3 plus grosses commandes françaises.

LINQ ≈ les Streams : Where = filter, Select = map, SelectMany = flatMap, GroupBy = Collectors.groupingBy, ToList = toList.

LINQ ≈ les itérateurs, et tout aussi paresseux : Where = filter, Select = map, SelectMany = flat_map, ToList = collect.

LINQ ≈ les compréhensions et les générateurs, en chaîne de méthodes. Where = if dans la compréhension, Select = l'expression, GroupBy ≈ itertools.groupby (sans le tri préalable).

LINQ ≈ les méthodes des tableaux, à une différence près : LINQ est paresseux, alors que filter et map créent un tableau à chaque étape.

var ids = orders
    .Where(o => o.Country == "FR")
    .OrderByDescending(o => o.Total)
    .Take(3)
    .Select(o => o.Id)
    .ToList();
var ids = orders.stream()
    .filter(o -> o.country().equals("FR"))
    .sorted(Comparator.comparing(Order::total).reversed())
    .limit(3)
    .map(Order::id)
    .toList();
let mut fr: Vec<&Order> = orders.iter().filter(|o| o.country == "FR").collect();
fr.sort_by(|a, b| b.total.cmp(&a.total));
let ids: Vec<u32> = fr.iter().take(3).map(|o| o.id).collect();
french = (o for o in orders if o.country == "FR")
biggest = sorted(french, key=lambda o: o.total, reverse=True)[:3]
ids = [o.id for o in biggest]
const ids = orders
  .filter(o => o.country === "FR")
  .toSorted((a, b) => b.total - a.total)
  .slice(0, 3)
  .map(o => o.id);

Asynchronisme : async/await et annulation

Exercise06/PageFetcher.cs télécharge des pages web avec HttpClient. Les tests utilisent un faux serveur (Support/FakeHttpHandler.cs) : pas besoin de réseau.

  1. FetchSizesAsync : télécharge toutes les pages en même temps et renvoie leur taille, dans l'ordre des adresses. Un test vérifie que les 3 requêtes se chevauchent bien.
  2. FetchSizesWithTimeoutAsync : abandonne une page au bout de timeout et renvoie -1 pour elle. Si l'appelant annule son CancellationToken, tout doit s'arrêter avec une OperationCanceledException.
en parallèle

Démarrez toutes les tâches, puis attendez-les ensemble avec Task.WhenAll. Un await dans une boucle foreach téléchargerait les pages l'une après l'autre. Une méthode async qui renvoie une liste se déclare async Task<IReadOnlyList<int>>.

un délai par page
using var timeoutSource = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
timeoutSource.CancelAfter(timeout);
qui a annulé ?

Pour distinguer « mon délai a expiré » de « l'appelant a annulé » : catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested).

Pièges à connaître : async void (réservé aux gestionnaires d'événements), .Result et .Wait() qui bloquent un thread et peuvent provoquer un interblocage, et le CancellationToken qu'on oublie de transmettre.

Comparaison

Task ≈ CompletableFuture, mais await évite les chaînes de thenApply. CancellationToken n'a pas d'équivalent direct : en Java, on interrompt un thread ou on annule un futur.

Task.WhenAll ≈ join_all : il attend toutes les tâches, puis relance l'exception s'il y en a une (try_join_all, lui, s'arrête à la première erreur). Contrairement à Rust, pas de runtime à choisir : le pool de threads est intégré, et une Task démarre dès qu'on l'appelle, sans attendre d'être .await.

Task.WhenAll ≈ asyncio.gather. Pas de boucle d'événements à lancer, et le code async peut aussi utiliser plusieurs cœurs.

Task ≈ Promise, Task.WhenAll ≈ Promise.all, CancellationToken ≈ AbortSignal. Comme en JS, une tâche démarre dès qu'on l'appelle.

var pages = await Task.WhenAll(
    urls.Select(url => http.GetStringAsync(url, cancellationToken)));
var futures = urls.stream()
    .map(url -> http.sendAsync(
        HttpRequest.newBuilder(URI.create(url)).build(),
        HttpResponse.BodyHandlers.ofString()))
    .toList();
var pages = futures.stream()
    .map(CompletableFuture::join)
    .map(HttpResponse::body)
    .toList();
let client = &client;
let pages = futures::future::try_join_all(urls.iter().map(|url| async move {
    client.get(*url).send().await?.text().await
})).await?;
async def fetch(session, url):
    async with session.get(url) as response:
        return await response.text()

pages = await asyncio.gather(*(fetch(session, url) for url in urls))
const pages = await Promise.all(
  urls.map(url => fetch(url, { signal }).then(r => r.text())));

[Fact]                                   // un test simple

Comparaison

Les tests vivent dans un projet séparé, qui référence le projet testé.

xUnit ≈ JUnit 5 : [Fact] = @Test, [Theory] = @ParameterizedTest.

Pas de #[cfg(test)] dans le même fichier : le projet de tests est à part, comme le dossier tests/ de Cargo.

xUnit ≈ pytest : [Theory] + [InlineData] = @pytest.mark.parametrize, Assert.Throws = pytest.raises.

xUnit ≈ Jest ou Vitest : [Theory] = test.each, Assert.Equal = expect(…).toBe(…).

[Theory]
[InlineData(2, 3, 5)]
public void Adds(int a, int b, int expected) =>
    Assert.Equal(expected, a + b);
@ParameterizedTest
@CsvSource({"2, 3, 5"})
void adds(int a, int b, int expected) {
    assertEquals(expected, a + b);
}
#[test]
fn adds() {
    assert_eq!(2 + 3, 5);
}
@pytest.mark.parametrize("a, b, expected", [(2, 3, 5)])
def test_adds(a, b, expected):
    assert a + b == expected
test.each([[2, 3, 5]])("adds %i + %i", (a, b, expected) => {
  expect(a + b).toBe(expected);
});
