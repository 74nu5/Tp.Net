Program.cs et un premier middleware

Ouvrez Program.cs. Il a trois parties, dans cet ordre :

  1. les services (builder.Services.Add…) : tout ce qui pourra être injecté ;
  2. le pipeline (app.Use…) : les middlewares que traverse chaque requête, dans l'ordre de déclaration ;
  3. les routes (app.Map…) : le code qui répond.

Complétez Diagnostics/RequestTimingMiddleware.cs : mesurez la durée de chaque requête, ajoutez-la à la réponse dans l'en-tête X-Request-Duration-Ms, et journalisez une ligne avec la méthode, le chemin, le code de statut et la durée. Branchez-le ensuite tout au début du pipeline.

Lancez l'API, appelez curl -i http://localhost:5080/ et regardez l'en-tête et la ligne de log dans la console.

mesurer

var stopwatch = Stopwatch.StartNew(); avant await next(context), puis stopwatch.ElapsedMilliseconds.

l'en-tête

Une fois la réponse commencée, les en-têtes sont partis : on ne peut plus les modifier après await next(context). Enregistrez plutôt un rappel avec context.Response.OnStarting(() => { …; return Task.CompletedTask; }).

le log et l'enregistrement

Un modèle de message, pas une interpolation : _logger.LogInformation("{Method} {Path} answered {StatusCode} in {ElapsedMs} ms", …). Chaque {…} devient un champ interrogeable. Enregistrement : app.UseMiddleware<RequestTimingMiddleware>();.

Comparaison

Un middleware ≈ un Filter de servlet, ou OncePerRequestFilter en Spring. L'ordre d'enregistrement dans Program.cs remplace @Order.

≈ axum::middleware::from_fn ou une Layer de tower : une fonction qui reçoit la requête et l'étape suivante.

≈ @app.middleware("http") de FastAPI ou un middleware ASGI : on reçoit la requête et call_next.

≈ un middleware Express : next est ici un délégué qu'on await, ce qui permet d'agir avant et après la suite du pipeline.

public sealed class TimingMiddleware(RequestDelegate next, ILogger<TimingMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var stopwatch = Stopwatch.StartNew();
        await next(context);
        logger.LogInformation("{Path} answered in {ElapsedMs} ms",
            context.Request.Path, stopwatch.ElapsedMilliseconds);
    }
}

app.UseMiddleware<TimingMiddleware>();
@Component
public class TimingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        long start = System.nanoTime();
        chain.doFilter(request, response);
        log.info("{} answered in {} ms", request.getRequestURI(),
                 (System.nanoTime() - start) / 1_000_000);
    }
}
async fn timing(request: Request, next: Next) -> Response {
    let path = request.uri().path().to_owned();
    let start = Instant::now();
    let response = next.run(request).await;
    tracing::info!(%path, elapsed_ms = start.elapsed().as_millis() as u64, "answered");
    response
}

let app = Router::new().route("/", get(root)).layer(middleware::from_fn(timing));
@app.middleware("http")
async def timing(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    elapsed_ms = int((time.perf_counter() - start) * 1000)
    logger.info("%s answered in %d ms", request.url.path, elapsed_ms)
    return response
app.use((req, res, next) => {
  const start = performance.now();
  res.on("finish", () =>
    console.log(`${req.path} answered in ${Math.round(performance.now() - start)} ms`));
  next();
});

Injection de dépendances et durées de vie

Le conteneur d'injection de dépendances est intégré : on enregistre un service dans builder.Services, et ASP.NET Core le fournit à qui le demande, en paramètre de constructeur ou de route. Chaque enregistrement choisit une durée de vie :

Durée de vieUne instance…Exemple typique
AddSingletonpour toute l'applicationcache, horloge, client HTTP partagé
AddScopedpar requête HTTPDbContext, unité de travail
AddTransientà chaque fois qu'on la demandepetit objet léger sans état

Diagnostics/Operations.cs définit trois classes identiques, qui tirent chacune un identifiant au hasard à leur création. Enregistrez SingletonOperation, ScopedOperation et TransientOperation avec la durée de vie que leur nom indique. Appelez ensuite GET /lifetimes deux fois, et observez quels identifiants changent.

Question

Que se passerait-il si un service singleton recevait un service scoped dans son constructeur ?

Voir la réponse

Le singleton garderait pour toujours l'instance de la première requête : c'est une captive dependency, source de bugs subtils (un DbContext partagé entre requêtes, par exemple). En développement, ASP.NET Core vérifie les portées et refuse de démarrer dans ce cas.

Comparaison

≈ le conteneur Spring : AddSingleton = scope par défaut, AddScoped = @RequestScope, AddTransient = @Scope("prototype"). Ici pas d'annotations ni de scan de classpath : tout se déclare dans Program.cs.

Rust n'a pas de conteneur standard : on partage explicitement avec Arc dans l'état de l'application et on crée le reste à la main. Le conteneur .NET automatise ce câblage.

≈ Depends de FastAPI, qui crée les dépendances par requête ; un singleton s'obtient avec @lru_cache.

≈ les scopes de NestJS (DEFAULT, REQUEST, TRANSIENT). Express seul n'a pas de conteneur.

builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IUnitOfWork, UnitOfWork>();
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();

le dépôt

Lire : db.Tickets.OrderBy(t => t.Id).Skip(…).Take(…).ToListAsync(ct), FirstOrDefaultAsync(t => t.Id == id, ct). Écrire : db.Tickets.Add(ticket) puis await db.SaveChangesAsync(ct). Supprimer sans charger : db.Tickets.Where(t => t.Id == id).ExecuteDeleteAsync(ct).

Comparaison

≈ Prisma ou TypeORM : le modèle C# joue le rôle du schema.prisma, et les migrations se génèrent de la même façon.

EF Core : requêtes, Include et le problème N+1

Les requêtes SQL envoyées par EF s'affichent dans la console de l'API (réglage Microsoft.EntityFrameworkCore.Database.Command dans appsettings.json).

  1. Créez trois ou quatre tickets, puis appelez GET /tickets/summary. Comptez les SELECT dans la console. D'où viennent-ils ? Corrigez GetSummariesAsync pour n'envoyer qu'une seule requête, quel que soit le nombre de tickets. Un test compte les commandes SQL.
  2. GET /tickets/{id} renvoie une liste de commentaires vide, même quand il y en a : EF Core ne charge pas les relations tout seul. Chargez-les dans GetAsync.
  3. Les lectures n'ont pas besoin du suivi des modifications : désactivez-le dans ListAsync et GetAsync. Un test vérifie que le contexte ne suit aucune entité après ces lectures.
N+1

Une requête pour les tickets, puis une par ticket pour compter ses commentaires : 1 + N. Une projection fait tout en une fois : db.Tickets.Select(t => new TicketSummary(t.Id, t.Title, t.Status, t.Comments.Count)). EF traduit Count en sous-requête SQL.

charger les commentaires

db.Tickets.Include(t => t.Comments).FirstOrDefaultAsync(…) : une jointure, dans la même requête.

sans suivi

db.Tickets.AsNoTracking()… en tête de requête.

Question

Pourquoi la version de départ fonctionne-t-elle quand même, et pourquoi le problème passe-t-il souvent inaperçu en développement ?

Voir la réponse

Elle donne le bon résultat, seulement trop lentement : avec 5 tickets en local, 6 requêtes passent inaperçues. Avec 5 000 tickets en production et un serveur de base distant, ce sont 5 001 allers-retours réseau. Lire les logs SQL pendant le développement est le meilleur réflexe.

Comparaison

Le même piège qu'avec Hibernate et les collections LAZY. Include ≈ JOIN FETCH, la projection ≈ une requête JPQL avec select new …, AsNoTracking ≈ une transaction en lecture seule.

Avec Diesel ou SQLx, on écrit la jointure soi-même, donc le N+1 est plus visible. Ici, LINQ le cache : il faut lire le SQL généré.

Le même piège qu'avec le chargement paresseux de SQLAlchemy. Include ≈ selectinload ou joinedload.

≈ include et _count de Prisma. Avec TypeORM, le même piège existe sur les relations paresseuses.

EF Core : écritures et seconde migration

On ajoute les commentaires et la clôture d'un ticket, avec sa date de clôture.

  1. Ajoutez une propriété DateTimeOffset? ClosedAt à Ticket, à TicketResponse et à son mapping.
  2. Générez et appliquez la migration : 
    dotnet ef migrations add AddClosedAt -o Data/Migrations

  3. Implémentez AddCommentAsync et CloseAsync dans EfTicketRepository : on ne commente pas un ticket clos, et on ne clôt pas deux fois.
  4. Ajoutez les routes POST /tickets/{id}/comments (201, 404, 409) et POST /tickets/{id}/close (200, 404, 409), et validez AddCommentRequest.

modifier une entité

Chargez le ticket avec suivi (sans AsNoTracking), modifiez ses propriétés, puis await db.SaveChangesAsync(ct). EF compare avec les valeurs d'origine et génère l'UPDATE.

ajouter un commentaire

ticket.Comments.Add(new Comment { … }) sur un ticket suivi, puis SaveChangesAsync : EF insère le commentaire avec la bonne clé étrangère.

Comparaison

EF génère la migration à partir du modèle, comme Liquibase avec son plugin Hibernate. Avec Flyway, on écrit le SQL soi-même.

Avec Diesel, on écrit up.sql et down.sql à la main ; EF les déduit du modèle C#.

≈ Alembic avec --autogenerate : même principe, à relire avant de l'appliquer.

≈ prisma migrate dev : même principe, le modèle fait foi.

dotnet ef migrations add AddClosedAt   # compare le modèle au dernier instantané
dotnet ef database update              # applique les migrations manquantes
dotnet ef migrations script            # le SQL, pour une mise en production relue
# Flyway : la migration s'écrit en SQL, à la main
cat > src/main/resources/db/migration/V2__add_closed_at.sql <<'SQL'
ALTER TABLE tickets ADD closed_at TIMESTAMP NULL;
SQL
mvn flyway:migrate
diesel migration generate add_closed_at   # crée up.sql et down.sql, vides
diesel migration run
alembic revision --autogenerate -m "add closed_at"   # compare les modèles à la base
alembic upgrade head
npx prisma migrate dev --name add_closed_at   # compare schema.prisma à la base, applique
npx prisma migrate deploy                     # en production

Écrire ses propres tests d'intégration

WebApplicationFactory<Program> démarre toute l'application en mémoire, sans port réseau : routage, validation, dépôt et SQL Server. C'est ce qu'utilisent tous les tests du TP, via Support/TicketsApiFactory.cs.

Dans tests/Tickets.Api.Tests/MyApiTests.cs, écrivez au moins deux tests. Quelques idées :

  • une priorité inconnue ("Urgent") est refusée avec une 400 ;
  • un ticket créé apparaît dans GET /tickets/summary avec zéro commentaire ;
  • un ticket supprimé disparaît du résumé.

Utilisez HttpExtensions.UniqueTitle(…) pour retrouver vos tickets : la base de test est partagée par tous les tests.

Pour aller plus loin

  • dotnet ef migrations script --idempotent : le script SQL qu'on relit et qu'on applique en production, plutôt que database update.
  • Ajoutez une route GET /tickets?status=Open : un paramètre de requête facultatif, filtré côté SQL.
  • Créez un fichier Tickets.Api.http : Rider et Visual Studio exécutent les requêtes HTTP qu'il contient, pratique pour garder des exemples d'appels.
